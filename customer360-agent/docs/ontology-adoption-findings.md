# 企業 AI 怎麼導入本體：架構結論（階段性，持續更新）

> 這份文件每完成一個實驗階段就更新一次。所有數字都能用 `experiments/` 底下的腳本重跑。
> **限制**：雲端環境連不到地端 Qwen，所以下面的實驗量測的是「架構對已知錯誤的攔截能力」，不是某個模型的答題能力。錯誤是依 LLM 常見失誤人工設計後注入的，真實錯誤的分佈要等接上 Qwen 再量。

## 一頁回答：企業 AI 應該怎麼導入本體？

**做法是：本體定義範本與詞彙 → LLM 讀題並填範本 → 本體執行 → SHACL／程式檢查（硬擋＋質疑）→ 再作答。不要讓 LLM 帶著本體自由推理，也不要只在最後檢查答案。**

```
本體 release（版號）
 ├─ 角色／部門範圍的 context 包      ← 權限在建包時就套用（C8：部門內整包塞入，跨部門先依本體切分再檢索）
 ├─ 本體型別化的 workflow 範本       ← 欄位型別＝本體類別；執行交給本體查詢，正確性由建構保證（C7）
 ├─ SHACL shapes（權威規格）         ← 跟本體一起發版；程式版是快速路徑，兩者用差異測試保證等價（C6）
 └─ 標籤／同義詞（錨點詞表）           ← 獨立重讀問題用（C3）

執行時：
 問題 → LLM 選範本、填欄位、必要時拆題（CoT 的產物是「範本呼叫」，不是自由文字）
      → 欄位型別檢查 → 本體執行 → 語意計畫
      → 硬擋（本體能確定推出的：存在、權限、OWL 推理、待定範圍、一致性）── 不過：帶錯誤重試，仍不過就拒答
      → 質疑（對照問題文字：歧義、錨點）──── 有疑問：把執行結果退回 LLM 一次 → 再檢查 → 仍有疑問就轉成向使用者澄清（C11）
      → 只帶已驗證的指標卡片作答 → 記錄質疑，回饋給本體維護（C4、C10）
 範本表達不了（約 1%～8%）→ 退回開放式語意計畫（plan 模式），一樣經過同一套檢查

多 agent 交接：agent A 的語意計畫 → 用接收方 agent B 的角色重新檢查並去敏（plan.handoff／MCP handoff_plan）→ 交給 B

本體改版時：質疑紀錄 → 維護待辦（backlog.md）→ 修改本體 → 回歸關卡（experiments/run_all.py）→ 發版
```

回答原本的問題：

- **本體和 CoT 的關係**：本體不放進自由的 CoT 裡讓模型自己推理。本體做兩件事：規定 CoT 必須交出的結構（範本呼叫或語意計畫），以及驗證這個結構。模型的思考內容可以保留來除錯，但只信任結構化的產物（C1）。
- **要不要先預先定義 workflow？** 要，而且是首選。3 個範本加上兩兩組合，可以表達 97% 的題目。但範本的欄位要交給 LLM 填：完全靠程式填，碰到沒見過的說法只剩 62%～69%（C7）。
- **由 SHACL 做檢查再執行？** 對，檢查放在執行之前，而且要檢查計畫而不只是輸出。SHACL 可以完整表達這套檢查（500/500 一致），前提是推理閉包和權限都先寫成資料，並用封閉世界的寫法檢查「計畫引用了什麼」。對照問題文字的檢查只能當質疑，不能直接擋（C2、C6）。
- **走向多 agent**：agent 之間交接的單位是語意計畫，不是自由文字。交接時用接收方的角色重新檢查並去敏（C12）。
- **質疑之後怎麼辦？** 退回模型一次，修改後再檢查，仍有疑問就問使用者。只退回模型會讓順從的模型把對的改錯；全部都問使用者又太打擾（C11）。
- **檢查要有獨立的第二讀者**：填欄位的一方和檢查的一方不能共用同一套判讀，否則會一起看漏（C3、C7）。

## 目前的結論（v10）

### C1. 本體進 CoT 的方式：要求交出「可檢查的中間產物」，而不是讓模型自由思考

模型不只交答案，還要交一份語意計畫：用語對到哪些類別、選了哪些指標、依賴哪些「是一種」判斷、排除了什麼。

- 在調參集上，只看最後輸出（決策＋指標）的檢查攔下 **65%** 的錯誤；看完整計畫的檢查攔下 **81%**。增加的部分全部來自「用語宣告和指標不一致」以及「排除條件」。這兩種錯，只有計畫裡寫出來才查得到。
- 推理過程的錯誤，例如編造類別、錯誤的 is_a，不一定讓最後指標出錯，但只要寫進計畫就 **100% 攔下**（三份題庫共 146 筆）。
- 換句話說，CoT 寫在自由文字裡無法檢查，寫成結構化計畫才能接上本體。

### C2. 檢查分兩級：硬擋只用本體能確定推出的事，對照問題文字的判斷只能「質疑」

| 等級 | 檢查內容 | 攔下錯誤計畫 | 誤擋正確計畫 |
|---|---|---|---|
| **硬擋** | ID 存在、權限（含總指標繼承分項拒絕）、OWL 推理的 is_a、待定範圍、用語與指標一致、排除條件 | 63%～67% | **0／89**（四份題庫） |
| **加上質疑** | 銀行／證券歧義、問題只提到一家卻選另一家、本體標籤錨點 | 98%～100% | 每份 0～2 題 |

- 對照問題文字的檢查，第一次碰到沒見過的說法時，誤擋了 **6/24 題（25%）**，例如「債券型基金」被當成問債券、「理專賣基金」沒被認出是銀行。修過兩輪後，在凍結規則才寫的第二份留出集上仍有 **2/16（12.5%）** 誤擋。
- 所以這類檢查不能直接擋，只能退回給模型：「問題提到『台幣』，你選的指標沒有涵蓋台幣商品，請確認」。模型確認原判斷就放行，質疑轉成作答時的提醒。實作在 `plan.SOFT_CODES` 與 `agent.py`。

### C3. 本體檢查抓不到「一致的錯誤對應」，需要一個獨立的第二讀者

如果模型把「基金手收」對成「ETF 手收」，而且把用語宣告也一起改成 ETF，整份計畫內部是一致的。這時存在性、權限、推理、一致性四層全部會放行：**0/11**。

- 解法是用本體自己的標籤當錨點，由程式獨立重讀問題。問題提到「基金」，選到的指標就必須涵蓋基金商品；問題問 AUM，指標就必須是 AUM。
- 加上錨點後，總攔截率從 **81% 升到 98%**；一致的選錯指標從 0/11 升到 11/11；一致的「用相近指標代替待定範圍」從 1/5 升到 5/5。
- 錨點是對問題文字的判讀，可能誤判，所以屬於 C2 的「質疑」等級。

### C4. 檢查能力的上限，就是本體詞彙的覆蓋率

留出集的誤擋和漏攔，幾乎都對應到本體缺的詞或概念：
- 「DCI」只存在指標名稱裡，本體沒有對應的商品類別。
- 「台幣計價」「外幣保單」被本體理解成存款專用的類別。
- 「海外債券型基金」裡的「海外」沒有對應的基金類別。

這代表質疑紀錄本身就是本體維護的輸入：哪些詞反覆觸發質疑、哪些質疑最後被模型確認是誤判，就是下一版要補的類別或同義詞。

### C5. 權限要沿著指標組成關係傳遞

目前的權限規則判定客戶可以看「證券總手收」，但它的分項含有客戶被禁止看的「證券複委託基金手收」，等於透過總數繞過規則。實驗中改成總指標繼承分項的拒絕，4/4 的越權都被硬擋下。這一條應該放回本體專案的權限計算。

### C6. SHACL 可以當檢查器，但要做到四件事；最好的用法是當「規格」，程式當「快速路徑」

把語意計畫轉成 RDF，和本體（含 OWL 推理閉包）、指標、權限規則放進同一張圖，用 `experiments/plan-shapes.ttl` 驗證。三份題庫的正確與錯誤計畫共 500 份：

| 比較 | 結果 |
|---|---|
| 硬擋判斷與程式版一致 | **500/500** |
| 質疑判斷、檢查代碼完全一致 | **500/500**（修正程式版一個語意漏洞後） |
| 速度 | 程式 0.7 ms；SHACL 約 0.28 秒（p95 0.39 秒） |

要做到等價，需要四個條件：

1. **OWL 推理的閉包要先物化成資料。** shape 只用單步 `rdfs:subClassOf`，不用 `*`／`+` 路徑；rdflib 碰到這類路徑會變得很慢。
2. **權限規則要寫成資料。** 包括組合規則、總指標繼承分項的拒絕，再用 SPARQL 約束判斷。
3. **用封閉世界的寫法，檢查「計畫引用了什麼」。** 計畫引用的每個 IRI 都必須是本體定義過的東西。58 筆自編指標 ID 全靠這類 shape 攔下。一般「只檢查有型別節點」的寫法，這 58 筆會全部悄悄通過，和外部文獻指出的 SHACL 盲點一致。
4. **中文斷詞、同義詞、否定詞留在程式。** 程式抽出問題特徵（提到哪些商品錨點、哪種指標、哪家子公司），寫成 `pl:mentions*` 三元組；「什麼情況要質疑」的規則留在 shapes。

**意外收穫**：用 SHACL 重寫歧義規則時，宣告式的寫法自然變成「每一個沒被選到的雙胞胎都要說明」。程式版原本是「選到任一雙胞胎就放過」，所以漏了實驗 1 剩下的 3 筆錯誤，也就是列舉題裡把整組銀行指標換成證券的情況。程式版改用同樣的判斷後，三份題庫的攔截率都到 100%，正確答案沒有新增誤擋。

**建議做法**：
- shapes 是給人審閱、跟著本體一起發佈版號的權威規格；程式版是線上的快速路徑。
- 兩者之間用差異測試保證等價：`tests/test_experiments.py` 每次抽樣比對。
- 檢查速度在 0.3 秒內，單題互動可以直接用 SHACL；高流量或批次場景用程式版。

### C7. 預先定義 workflow 優先，但「填欄位」交給 LLM；只有拆不進範本的才讓 LLM 自由組計畫

把常見意圖寫成本體型別化的範本，只做了三個：
- `metric_lookup(種類, 商品, 子公司, 排除, 總指標, 縮寫)`；
- `concept_is_a`；
- `concept_relation`。

範本的欄位型別都是本體類別，執行完全交給本體查詢，所以結果一定符合本體，正確性由建構保證。用三份題庫 73 題實測（不需要模型）：

| 做法 | 調參集 | 留出集 1 | 留出集 2 | 合計 |
|---|---|---|---|---|
| 範本＋程式依本體標籤填欄位（完全不用 LLM） | 85% | 75% | 62% | **77%** |
| 範本表達上限（欄位一定填對） | 97% | 83% | 81% | **89%** |
| 允許組合兩個範本呼叫（LLM 拆解問題） | — | — | — | **95%** |
| v5：欄位加入指標名稱裡的限定詞（信託、自營、DCI…）後，程式填欄位 | 85% | 79% | 69% | **79%** |
| v5：同上，範本表達上限 | 97% | 88% | 88% | **92%**（組合兩個範本：**97%**） |

- **三個範本就能表達 89% 的題目，組合兩個範本可以到 95%。** 這類問數題，絕大多數不需要讓 LLM 自由組計畫。
- **難的是填欄位。** 程式填欄位在調參集是 85%，碰到沒見過的說法掉到 62%（實驗 4 修正檢索與補上「規模→AUM」後，合計 75%→77%）。例如「股票型 ETF 規模」被當成概念題，「信託的海外債」抓不到信託。這正是 LLM 該負責的部分：讀懂問題，填範本欄位或拆成多個範本呼叫。
- **workflow 失敗時偏保守。** 失敗的題目多半回答「不在範圍」（11 題），默默答錯只有 6 題。
- **v5 把指標名稱裡的限定詞（信託、自營、DCI、ELI…）加進範本欄位後**，「信託的海外債」「自營的外國債券手收」也表達得了，組合後上限到 97%，只剩 2 題（台股、加總推理）。但這只是借名稱暫代：信託／自營其實是通路維度，應該成為本體的類別。
- **（v4）組合後仍表達不了的 4 題：**
  - 3 題是本體缺概念：「信託／自營」這種通路區分、「台股」，目前只寫在指標名稱裡，沒有對應類別。這要靠本體補類別，換範本解決不了。
  - 1 題需要真正的推理：「總 AUM 加上分項，是不是全部資產」。
- **獨立性很重要。** workflow 的 6 個默默答錯，本體檢查硬擋 0 個、質疑只抓到 3 個。因為程式填欄位和錨點檢查用的是同一套詞表，兩者會一起看漏。要讓檢查有效，填寫的一方和檢查的一方必須是不同的讀者：LLM 填欄位、詞表檢查，或反過來。

和外部做法一致：Palantir 讓 agent 只能透過型別化的 Action 改資料；Anthropic 的建議是能用 workflow 就先用 workflow，只有無法預測步驟的開放問題才交給 agent。

### C8. 本體規模在部門內就整包塞入；跨部門要先依本體切分範圍再檢索，並用本體關係擴充檢索結果

| 檢索前 k 名 | 全部期望指標都找到 | 加上本體擴充（同名指標、總指標與分項、同商品指標） | 估計 token |
|---|---|---|---|
| 1 | 57% | **88%** | ≈3,000 |
| 3 | 93% | 97% | ≈4,500 |
| 5 | 95% | **100%** | ≈5,400 |
| 整包理專 context（44 項指標） | 100% | — | ≈4,500 |

- **現在的規模，整包塞入比較好。** 檢索到 100% 召回時（約 5,400 token），反而比整包 context（約 4,500 token）還大，而且多了一個會出錯的步驟。
- **整包塞入有上限。** 每項指標在 context 裡約佔 65 token：200 項約佔 32k context 的 45%，500 項就超過整個 context。金控層級的指標動輒數百上千項，一定要分段。
- **用本體擴充檢索結果的效果很大。** 只取第 1 名時，全中率從 57% 升到 88%。因為歧義題要兩邊的同名指標、總指標題要分項，這些都是本體關係帶出來的，單純的文字相似度做不到。這就是「本體引導的檢索」。
- **建議的分段方式就是本體本身。** 部門採用哪些指標（`fh:usesMetric`）和角色權限，天然把範圍切成部門大小。先依部門與角色決定範圍，範圍內整包塞入；跨部門的問題再先檢索、後擴充。
- **檢索器本身也要迭代。** 最初的召回在長問句上失敗（前 8 名＋擴充只有 93%）。改成餘弦式正規化、忽略「指標」「哪個」這類通用詞、名稱只用主幹計分，再補一個同義詞後，才到 100%。這些修正有一部分是看著留出集 1 做的，所以 100% 是調整後的數字。

### C9. 同一個讀者、五種架構：差別只在本體怎麼進入流程

為了在接上 Qwen 之前就看到架構本身的效果，用同一個只會做關鍵字檢索的替身當「模型」（`--backend heuristic`），跑調參集 33 題：

| 模式 | 正確 | 默默答錯 | 保守未答 |
|---|---|---|---|
| baseline（平鋪資料字典） | 33% | 22 | 0 |
| context（角色 context 包，不強制檢查） | 33% | 22 | 0 |
| plan（語意計畫＋強制本體檢查） | 46% | **8** | 10 |
| tools（工具查詢＋強制本體檢查） | 46% | **8** | 10 |
| workflow（填範本＋本體執行＋檢查） | **76%** | 3 | 5 |

（v7：質疑改為「退回→再檢查→仍有疑問就問使用者」後，workflow 的默默答錯從 5 降到 3。）

讀題能力完全相同，加上強制檢查後，默默答錯從 22 題降到 8 題（多數轉成保守未答）；改成範本由本體執行後，正確率再升到 76%。這是流程檢查，不是模型能力；真正的數字要用地端 Qwen 跑 `scripts/c360a eval` 取得。

### C10. 本體維護是一個迴路：質疑紀錄 → 修改本體 → 回歸關卡 → 發版

- **質疑紀錄會自動變成待辦。** `scripts/c360a backlog runs/<資料夾>` 把每次評測的質疑分成三類：
  - **誤質疑**：最後被接受的計畫仍被質疑，但答案正確 → 可能要補本體；
  - **促成修正**：中途被質疑，模型之後改對 → 檢查有用；
  - **答案仍錯**。
- **在沙盒照待辦補了 3 個類別**：台股商品、信託投資商品、自營商品，並對應到 5 項指標。量測結果（細節見 `docs/ontology-proposal-20261101.md`）：
  - 範本表達上限從 89% 升到 **93%**，組合後從 95% 升到 **99%**，只剩「加總推理」1 題。
  - v5 借指標名稱暫代的做法不再需要：開或關，結果完全一樣。
  - 硬擋誤擋三份題庫仍然都是 **0**。
- **但新詞會帶來新的質疑。** 本體認得「台股」之後，「證券總手收有沒有包含台股手收？」被質疑「選到的指標沒有涵蓋台股」，而這正是正確答案的內容。本體每加一個詞都可能改變檢查行為，所以改版前一定要跑回歸。
- **回歸關卡**：`experiments/run_all.py` 跑完四個實驗並檢查門檻。
  - 門檻：硬擋誤擋 = 0；注入錯誤攔截率 ≥ 95%；SHACL 與程式一致 100%；組合表達上限 ≥ 90%；檢索召回 ≥ 95%。
  - 不過就回傳非 0，可以接在本體專案的 `release` 之前。
  - 正式本體與沙盒版本都通過。

### C11. 質疑之後：退回模型一次 → 再檢查 → 仍有疑問才問使用者

質疑可能誤判（C2），模型被質疑後也可能「附和翻盤」，把對的改錯。實驗 5 取三份題庫中只被質疑、沒有硬擋的計畫，包括 69 份錯誤計畫和 3 份被誤質疑的正確計畫。模型的反應模擬成三種：一律堅持、一律照改（順從）、錯才改（理想）。

| 處理方式 | 錯誤計畫仍默默答錯 | 正確計畫被改錯 | 需要問使用者 |
|---|---|---|---|
| 只在回答附上質疑 | 69 | 0 | 0 |
| 一律問使用者 | 0 | 0 | 72 |
| 退回模型（順從型） | 22 | **3／3** | 0 |
| 退回模型（理想型） | 22 | 0 | 0 |
| **退回模型 → 再檢查 → 仍有疑問才問使用者**（順從型） | **8** | **0** | 19 |

- 只退回模型，順從型模型會把 3 份被誤質疑的正確計畫全部改錯。例如「台幣計價的基金」被改成台幣存款。
- 退回後再跑一次檢查，就能攔下這些翻盤，因為改錯的計畫本身又會被質疑。默默答錯從 69 降到 8，翻盤歸零，使用者只需要介入 19 次（26%）。
- **試過但比較差的細分**：「最後只剩錨點缺漏（指標範圍比問題廣）時照答附說明，其他才問使用者」。這能少問 9 次，但默默答錯從 8 升到 16，順從型模型的翻盤也回來（3 份）。原因是很多選錯同類指標的錯誤，表面上只會觸發錨點缺漏。結論：仍有疑問就一律升級；多問的那幾次是值得的代價。
- agent 現在預設就是這個做法（`agent.challenge_policy: escalate`）；要回到「照答附提醒」可以改成 `warn`。
- 這是模擬的模型行為。Qwen 實際是哪一型，要看評測報告裡被質疑後的計畫怎麼變；`backlog.md` 的「促成修正」與「誤質疑」可以直接看出來。

### C12. 多 agent 交接：交接的單位是語意計畫，接收前用接收方的角色重檢並去敏

假設理專 agent 的答案要交給面對客戶的 agent 使用。三份題庫中理專／私銀主管的正確計畫共 55 份，其中 49 份含有客戶不可看的指標，共 67 個：

| 交接方式 | 漏給客戶的指標 |
|---|---|
| 不檢查直接交接 | 67 |
| 用 Studio 原本的權限規則（沒有總指標繼承） | 1（證券總手收） |
| **接收方角色重新檢查並去敏**（`plan.handoff`，MCP 工具 `handoff_plan`） | **0** |

- 49 份是拿掉對方不可看的指標後再交接，不是整份擋掉；全部被拿掉的就改成「不在範圍」。
- 這驗證了你原本的設計立場：權限綁定 agent 自己能取什麼資料；本體檢查約束 agent 的輸出能不能交給另一個 agent。兩者是同一套規則在不同時點執行，不用重複建置。
- 能做到去敏，是因為交接的是結構化計畫。如果交接的是自由文字回答，就只能整段放行或整段擋掉，沒辦法可靠地只拿掉其中一項指標。

### C13. 成本：workflow 模式最省

依各模式實際送出的 prompt 估計理專角色每題的輸入 token（實驗 7；真實數字以 Qwen 評測的 usage 為準）：

| 模式 | 每題輸入 token（估計） |
|---|---|
| baseline | ≈2,900 |
| context | ≈4,700 |
| plan | ≈6,200 |
| tools | ≈2,600 起（加上工具結果與多輪） |
| **workflow** | **≈3,400** |

workflow 不必把指標清單整包送進去，只送類別骨架與範本說明，再加上作答階段的已驗證指標卡片，所以比 context 和 plan 都省。這還沒計入 Qwen3 的思考 token；思考開啟時，輸出可能是答案的數倍。

### 最終首次接觸驗證（留出集 3）

所有規則調整都完成後，另寫 16 題從沒見過的題目（`eval/holdout3.yaml`），一次量完、不再修改：

| 項目 | 留出集 3 | 四份題庫合計 |
|---|---|---|
| 硬擋誤擋正確答案 | **0/16** | **0/89** |
| 質疑誤擋正確答案 | 1/16（「美元計價的海外債券基金」） | — |
| 注入錯誤攔截率（硬擋／加上質疑） | 64%／98% | — |
| workflow 程式填欄位 | 12/16（75%） | — |
| workflow 範本表達上限／組合後 | 15/16／**16/16** | — |

workflow 程式填欄位失敗的 4 題，正好是該交給 LLM 的部分：
- **口語詞沒收錄**：「活存定存」不是本體詞彙；「部位」應理解為 AUM。程式找不到指標種類，因此答錯或答不了。
- **一句問兩件事**：「黃金的手收和外匯的手收」要拆成兩個範本呼叫。
- **修飾語**：「美元計價的海外債券基金」。

這也再次說明本體與 LLM 的分工：本體負責「什麼是對的、能不能做」；LLM 負責「使用者在問什麼」。「活存」「定存」「部位」這類詞，則透過質疑紀錄回補到同義詞表（C4、C10）。

### 實驗 1 的設計

- **正確計畫（gold plan）**：只用題庫的期望欄位和本體推得，不手寫答案。用語的類別取期望指標最具體的共同上層，再加上共同的商品類別。
- **17 種錯誤**：
  - 自編指標或類別 ID；
  - 選錯同類指標（分兩種：用語宣告不變，或連宣告一起改成一致）；
  - 只答銀行或證券一邊、把銀行換成證券（或反過來）、該澄清卻直接答；
  - 越權、透過總指標越權；
  - 用相近指標代替待定範圍（分兩種：用語宣告誠實，或一致地改寫）；
  - 錯誤的 is_a；
  - 忽略否定條件（分兩種：有寫排除，或連排除都沒寫）；
  - 總指標與分項並列、引用舊版號。
- **確實錯誤**：每一筆錯誤計畫都先交給評分器，只有評分器判為「不正確」的才計入攔截率。版號引用錯誤和總指標並列屬於良性，評分器不判錯，所以不計。
- **四份題庫**：
  - 調參集 33 題；
  - 留出集 1（24 題）：寫完後用來修過兩輪規則，已不算沒見過；
  - 留出集 2（16 題）：規則凍結後才寫，只量首次接觸的誤擋；
  - 留出集 3（16 題）：v8 全部調整完成後才寫，最終的首次接觸驗證。

（v2：歧義改為逐一檢查每個沒被選到的雙胞胎，原本漏掉的 3 筆列舉題錯誤也被質疑；誤擋數不變。）

「只看輸出」也包含錨點質疑。錨點直接對照問題和指標，不需要計畫，所以補回了大部分差距。完整計畫多出來的是否定條件、用語宣告不一致這兩類。

v1 時仍然漏掉列舉題裡「把整組銀行指標換成證券」的錯誤，例如「結構型商品的手收有哪些」。v2 在實驗 2 中修正了這一點。

### 迭代過程（每輪都是先量測，再修改）

1. 第一版（L1～L5）：完整計畫攔下 77%，一致的錯誤對應 0%。→ 加入本體標籤錨點（L6）。
