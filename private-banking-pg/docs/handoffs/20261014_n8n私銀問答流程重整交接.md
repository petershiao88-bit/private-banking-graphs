## 現行流程為何不直覺

現行主要順序是：

```text
Graph Chat
→ Read QA Memory
→ Prepare Dialogue
→ Aura - Full Concept Graph
→ Resolve Followup
→ KB Input
→ Needs Mapping?
```

概念或澄清分支走 `Concept Evidence`，直接送 `Prepare Evidence Packets`。計算分支如下：

```text
Jev - Prepare Concept Paths
→ Scope Concept Request
→ Jev - Concept Path Decisions API
→ Concept Path Result
→ Retain Selected Concepts
→ Aura - Mapping Paths
→ KB Result
→ Compact Graph Evidence
→ Prepare Evidence Packets
```

共用回答流程為：

```text
Read Evidence → Combine Evidence Notes → Multiple Packets?
→ Compose Answer 或 Use Direct Answer
→ Validate Answer → Grounded Identifiers?
→ 通過則 Finalize QA
→ 未通過則 Repair Answer → Verify Repaired Answer → Finalize QA
→ Write QA Memory → Graph Chat Response
```

辅助節點為 `Question Schema`、`QA Chat Model`、`QA Text Memory`。

`Resolve Followup` 的節點 Input 雖是完整圖譜回覆，其 LLM 提示詞實際只取產品代碼、名稱與別名，另加原問題、歷史對話與上一輪主題，沒有把完整圖中所有關係送給該 LLM。它目前不只補全追問，還判斷產品、領域與證據深度。

`Scope Concept Request` 又依 Resolve 的產品與領域先篩候選，因此 Jev 常只是在確認前面已選好的路徑。使用者希望取消這層重複產品判斷。

```text
├─ 讀對話記憶 → 整理原問題與必要對話脈絡

→ 一個 Code 整理 Jev 結果及選中概念
├─ 概念說明 → 用相關概念證據回答
├─ 計算說明 → 查映射 → 一個 Code 整理計算證據 → 回答

└─ 無法支援 → 說明目前資料能回答的範圍及缺口

```

移除前置 `Resolve Followup`、其專用 `Question Schema` 與 `Scope Concept Request` 產品預篩選。舊 `KB Input`、`Needs Mapping?` 等引用也需跟著新分支調整，不能只改畫布而保留舊命名引用。

原問題、必要記憶與完整概念圖交給 Jev。對話中的歷史回答只用於理解指代，不可當成業務事實證據；本輪明確條件取代上輪對應條件。沒有記憶時輸出空陣列，不能讓 Merge 永久等不到資料。

請區分兩條資料分支與真正並行。現行 `executionOrder=v1` 不應承諾同步耗時優化。[n8n 官方執行順序](https://docs.n8n.io/flow-logic/execution-order/)與 [Merge 文件](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.merge/)已核對。

## Jev 分支與回傳合約

現行 Jev 使用 `POST https://openrouter.ai/api/alpha/decisions`，請求為 `model`、`state`、`questions`。模型目前指定 `typesafe/jev-1.13`。每條路徑是一個 `type=choice` 問題，選項為 included／uncertain／excluded，可同時納入多條。不要改成只能選單一路徑的 top-1。

建議在同一份 `questions` 增加一個流程判斷，名稱可由接續實作者決定，但應涵蓋：

| 處理狀態 | 意義 |
|---|---|
| 概念說明 | 問定義、分類、角色或業務範圍，用概念證據即可 |
| 計算說明 | 問計算、日期、彙總等，需沿所選路徑查映射證據 |
| 需要澄清 | 問題加記憶仍有無法消除的產品、通路、指代等歧義 |
| 無法支援 | 問題清楚，但目前圖譜或資料能力未涵蓋所需內容 |

這是應用程式的處理分支，不是 Neo4j 中新增一條「無法回答」业务關係，也不能當成普通 selectedPaths 送入映射查詢。

Jev 支援多個 typed questions 在一次呼叫中返回答案，也支援自訂 choice 選項；它不產生澄清問句或自由文字理由。[OpenRouter 官方 Jev 說明](https://openrouter.ai/blog/insights/what-is-jev/)已核對。需要追問時可用既有回答模型組句，或使用明確的問題模板，不必每輪另叫一個 Resolve LLM。

這些判斷不是先選路再由模型讀回自身答案，應提供同一份完整 state 與清楚的判斷說明。不同 questions 可能回傳不一致結果，Code 必須核對。例如選「計算說明」但沒有 included 路徑時，不能照常查映射；不能把「沒納入路徑」一律判成使用者問得不清楚。

概念題如「AO 是什麼」可能不需要任何金額衡量路徑，不能因 selectedPaths 為空就一律拒答。實作時須決定怎麼保留相關概念／關係給概念分支，並確保不恢復把完整候選評分往後傳的問題。

Jev 看概念圖只能判斷是否可以繼續查證，不能提前保證映射規則完整或能報實際金額。本系統是理解圖譜與運算邏輯的問答測試，不含交易金額查詢；問實際金額時應如實說明能力限制，不必追問月份後又假裝可以查金額。

## Code 合併方案與資料引用

| 現有節點 | 接續方向 |
|---|---|
| Jev - Prepare Concept Paths ＋ Scope Concept Request | 改成一個準備 Jev 輸入的 Code，取消產品預篩；由 Merge 提供問題、記憶與圖 |
| Concept Path Result ＋ Retain Selected Concepts | 合成一個處理 Jev 結果的 Code：解析原生答案、核對狀態、保留 included 路徑與必要上下文、輸出分支資料 |
| KB Result ＋ Compact Graph Evidence ＋ Prepare Evidence Packets | 合成計算證據整理 Code：解析映射、整理引用與規則、保留依賴、去重並按既有資料量上限輸出證據包 |

合併不代表刪除檢查。需保留多對多映射、父子範圍重疊、全部必要來源依賴、規則各版本、精確去重、完整 SQL 語意證據、每包 96,000 bytes／至多 32 包等既有邊界，不截斷單一規則或來源文字。

合併後目前依靠舊節點名稱的引用都會失效。尤其要核對 `$('KB Input')`、`$('Concept Path Result')`、`$('Retain Selected Concepts')`、`$('Compact Graph Evidence')`、`$('Prepare Evidence Packets')`，以及 `.all()` 對多份證據包的引用。`Combine Evidence Notes`、`Validate Answer`、`Verify Repaired Answer`、`Finalize QA`、記憶 sessionKey 與回覆節點都可能需改引用。

原生完整 Jev 答案留在 Jev API 節點，候選定義留在準備請求節點。下游只保留需要的選取結果、處理狀態、必要上下文及可追查 requestId。不要把全部 answers／候選概率重新放進回答提示。

目前記憶 topic 來自 Resolve 的 `topic`，移除 Resolve 後需另訂儲存合約。可從 Jev 選中的產品與領域保存可確定的主題，保留原問題與有限文字對話；多產品題不能硬縮成單一產品。日期、通路等條件不得由未驗證的推測加入。記憶僅保存文字問答與主題，維持最近最多 12 輪及 32,000 bytes 限制，不保存完整圖譜、工具輸出或 SQL。

## 回答改為業務語言

目前 `Read Evidence`、`Compose Answer` 提示要求列底表、來源 key、ruleId／statementKey；`Repair Answer` 強調依核對 SQL 解釋來源與計算。這些設定造成表名與技術描述外露，三處都要調整，包含單包直接回答及多包整合兩條出口。

預設回答先直接說結論，再描述必要的業務運算流程：

- 哪些交易、產品、客戶或業務範圍納入，哪些被排除。
- 金額的意義、計算方式與彙總粒度。
- 日期、月份歸屬、估值或幣別規則。
- 不同資料如何合併，哪些重複項目會被排除。
- 會影響結果的限制、衝突與待確認條件。

表名、欄位代碼、SQL 關鍵字、內部 key、包編號與來源行號預設不出現在使用者回答。使用者明確要求技術來源或 SQL 時才展開。保留內部證據核對，不要為了白話而刪除會改變運算結果的規則，或用常見金融公式補缺口。

基金收入的表達例子：先依客戶與收入月份彙總交易收入；交易日期達到該月倒數第二工作日或之後，歸入次月，較早交易歸入當月；兩批彙總結果合併時，完全相同的輸出只保留一次；另有資料截至日期限制及待確認業務適用性。

此例中的去重是來源實作中完整彙總列的去重，不代表已按交易唯一鍵去除每一筆重複交易。白話描述不能把兩者混為一談。第二批基金資料引用債券來源最大日期的疑義，也應以業務上的日期適用性說明，不能隱藏。
