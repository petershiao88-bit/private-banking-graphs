四、確認過的程式行為與缺陷（仍未修正）

程式：deliverables/single_turn_qa/rag_v1/graph_retrieval_v8/retrieval.cjs
設定第 2 行：anchorCandidates=24、semanticAnchors=4、compactnessMargin=0.05。
prepare 第 15 行；retrieveAnchors 第 28 行；buildSpecs 第 39 行；candidateBundles 第 70 行；selectSubgraph 第 117 行。

A. 相關性過早被當成查圖角色
前 4 名直接按商品、指標、property、concept 分類生成查圖規格，沒有獨立判斷候選是查詢對象、篩選條件、指定目標或僅相關背景。
商品與指標混在一起時，指標可能成為路徑目標；沒有商品時，每個指標建立獨立反向組成與順向歸屬候選。
property 目前是正向欄位值，沒有完整處理「不屬於／不包含」的運算子。

B. 每分組必留一個
第 11 節點依 groupId 分組，每組通常取最高分；若有差 0.05 以內、保留同樣商品與衡量綁定的嚴格子圖，可能改選較小候選。
目前沒有判斷整個分組是否不相關並淘汰的步驟。因此前面誤建的分組會繼續留下候選。

C. 硬補入口（第 133 行）
for (const a of p.selectedAnchors) ... graph.nodes.push(n)
所有選中入口中有 key 的商品、指標、concept，若不在已選路徑裡，仍會補回節點。
只補節點，不補被淘汰的整條路徑或關係；property 候選沒有 key，不會依此規則補回。
此行在第 11 節點，不是最後第 13、14 節點。
後續應移除無條件補回；商品清單的合法獨立節點可由 identity 候選保留。

D. 複數商品的路徑評分
商品通常共用一個查詢範圍，分 AUM／收入生成候選；不是每商品各選一條最高分路徑。
例如基金與 ETF 會組成「兩商品到最近可達指標」「兩商品到共同上層指標」等整組候選，Rerank 每組一個分數。
共同終點候選有檢查覆蓋所有起點；最近一層 frontier 只依實際查到的路徑組成，未同樣保證每個指定商品都有有效路徑。
可能出現某商品無路徑、卻在最後硬補成獨立節點，讓表面商品數看似完整。
缺路徑不能以補裸節點冒充覆蓋成功。

E. 去重已存在，不能誤報為完全沒去重
mergePaths 在每個候選子圖內按節點 key、關係 id 去重，共用指標只保留一份。
同一 groupId 內，節點與關係集合完全相同的候選依 signature 去重。
不同商品到同指標的兩條關係不是重複，必須保留；不同停點候選也要保留供比較。
最終合併再去重，但去重不能解決語意多取。

討論中的流程：
原句 → 擷取單詞／重疊片語 → 原句與詞組批次 Embedding → 分別向量檢索 → 按候選 ID 合併去重並保留詞組來源 → 原完整問題 Rerank → 選入口 → 查圖。
完整片語作主要訊號、泛詞作補充是待驗證策略，尚未選定權重或合併算法。
原句必須保留需求、商品配對、複合條件與否定語意，不能把「不屬於證券」只剩「證券」。
詞組仍走語意檢索；沒有恢復字面命中保送或問題類型路由。
若合併後候選集合仍與原先完全相同，且使用同樣的原句、候選文字做 Rerank，切詞本身不會自動修復入口角色混淆；需實測實際候選及後續結果。
既有這 33 題的必要候選已全召回，因此不要把新增詞組的召回提升預先當成已證明。

官方 Embedding API 沒有用一個參數自動擷取上述語意詞組的功能；它接受多筆文字，回傳每筆的向量。
可以透過 OpenRouter 呼叫支援結構化輸出的文字 LLM，要求只回傳原句與詞組 JSON，再批次送 Embedding。
也可以在 n8n 程式端做斷詞／片語組合；目前未安裝斷詞套件、未選模型，未建立新節點。
