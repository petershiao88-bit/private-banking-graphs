## 1. 專案目標與目前架構

正在製作私銀 AUM 智能查詢 prototype，使用 n8n＋Supabase PostgreSQL＋LLM。

目前主流程：

```text
User Query
→ Router Input
→ Metric Registry / Aggregate
→ Metric Router
→ Switch
   ├─ executable_match → Direct Metric → Normalize Result
   └─ no_executable_match → SQL Reasoning Agent
                              ├─ SQL KB tool
                              ├─ Postgres Chat Memory
                              └─ SQL Model
                              → Execute SQL
                              → Repair loop（如有錯誤）
→ Response LLM
```

已確認：

- `executable_match` 路徑可正常執行直接 Metric SQL。
- `no_executable_match` 路徑可呼叫 SQL KB 並生成 SQL，但目前會遺漏 stage 與錯誤處理彙總粒度。
- Simple Memory 已在主流程改為 `Postgres Chat Memory`；但「我剛剛問了哪些問題」仍被 Metric Router 當成不支援的 Metric，這是另一個記憶路由問題，不是目前 SQL KB 主線。

## 4. n8n SQL KB 與 SQL Agent 的實際排查結果

重要執行紀錄：主 workflow execution `#2261`。

使用者問題：

```text
2026 年 8 月底，存款 AUM 超過 1,000 萬元的客戶共有幾位？
```

n8n 回答：`0 位`，但預期應為 `1 位`。

### 4.1 SQL KB 並沒有少回傳 stage

SQL KB tool 當次實際回傳 index 0～9，包含：

- TMP01～TMP08
- `STG_AUM_005_007_008_009`
- `STG_AUM_FINAL_ROLLUP`

因此「Agent 只用 TMP01～TMP03」不是因為 SQL KB 少了 TMP04～TMP08。

### 4.2 SQL KB 回傳的底表與 Metadata 是空的

當次 tool output 顯示：

```text
source_tables: []
table_metadata: []
```

但本地 v0.2 CSV 中有正確 `source_tables_json`。

n8n 子流程的 `Staging SQL` Data Table node 目前選擇名稱為：

```text
AUM Staging SQL KB v0 1
```

後續要檢查實際 Data Table 版本，並改用／重新匯入 v0.2，或補齊 v0.1 中缺少的 `source_tables_json`。

### 4.3 主 Prompt 欄位名稱不一致

目前 Prompt 寫：

```text
依 stage_level 與 depends_on_json
```

但 SQL KB tool 實際回傳：

```text
depends_on
```

應統一為 `depends_on`。

### 4.4 Agent 遺漏了 stage

SQL Reasoning Agent 最後只產生：

```text
TMP01
TMP02
TMP03
AUM_005_007_008_009（也只 UNION 上述三個 CTE）
```

即使 tool 已回傳 10 個 stage，Prompt 沒有 `expected_stage_count` 或 dependency closure 的硬性檢查，因此模型可能自行簡化，也可能受 output token 長度影響。

### 4.5 最終查詢的彙總粒度錯誤

錯誤寫法：

```sql
WHERE 存款AUM > 10000000
```

這是在各底表的單筆／分類結果上判斷門檻，而不是在「客戶月底存款總 AUM」上判斷。

正確順序：

```text
底表轉換
→ 選擇當期有效來源
→ 合併存款部位
→ 依 cust_id＋yyyymmdd 彙總
→ 得到 customer_deposit_aum
→ 套用金額門檻／排名／客戶計數
```

### 4.6 不能盲目強制使用所有 TMP

TMP01 與 TMP06、TMP02 與 TMP07、TMP03 與 TMP08 使用相同底表，且原始日期條件在 2026 年可能重疊。

若 Agent 直接把 TMP01～TMP08 全部 `UNION ALL`，可能重複計算。因此正確解法不是「要求 Agent 每次全用」，而是在 KB 層先根據日期與版本選出 `active_stages`。

### 4.7 `STG_AUM_FINAL_ROLLUP` 對存款 Metric 過度擴張

`STG_AUM_FINAL_ROLLUP` 對應總 AUM，還依賴投資、保險、證券等未建立的 staging objects。

純存款 Metric 應以：

```text
STG_AUM_005_007_008_009
```

為 target object，不應強制使用 global AUM final rollup。

## 6. 建議新增的規則資料模型

不要只新增一大段自然語言說明，應盡量使用結構化欄位。

### 6.1 `metric_execution_rules`

一個 Metric 一份語意執行契約。

```text
metric_code
target_object
output_grain_json
group_by_columns_json
measure_column
measure_aggregation
supported_dimensions_json
supported_operations_json
aggregate_before_threshold
threshold_stage
date_rule_json
version
active
```

存款 AUM 範例：

```json
{
  "metric_code": "aum_deposit_month_end",
  "target_object": "AUM_005_007_008_009",
  "output_grain": ["cust_id", "yyyymmdd"],
  "group_by_columns": ["cust_id", "yyyymmdd"],
  "measure_column": "存款AUM",
  "measure_aggregation": "sum",
  "supported_operations": [
    "detail",
    "sum",
    "count",
    "threshold",
    "ranking"
  ],
  "aggregate_before_threshold": true,
  "threshold_stage": "after_customer_aggregation"
}
```

### 6.2 `source_table_usage_rules`

說明每個 Metric 在不同日期下可使用哪些底表，並解決新舊版本重疊。

```text
metric_code
source_table
table_role
date_column
valid_from
valid_to
priority
mutually_exclusive_group
deduplication_keys_json
filter_rules_json
version
active
```

### 6.3 Staging SQL KB 建議補充欄位

```text
valid_from
valid_to
priority
mutually_exclusive_group
required
```

也可以另建 `metric_stage_rules`，避免直接改現有 Staging SQL KB：

```text
metric_code
staging_sql_id
required
valid_from
valid_to
priority
mutually_exclusive_group
active
```

## 7. SQL KB 子流程的目標輸出

主流程不要分別呼叫四次再由 Agent 拼接。SQL KB 子流程應接收：

```json
{
  "metric_code": "aum_deposit_month_end",
  "as_of_date": "2026-08-31",
  "requested_operation": "count_threshold"
}
```

並一次回傳完整 execution package：

```json
{
  "metric_code": "aum_deposit_month_end",
  "supported": true,
  "unsupported_reason": null,
  "execution_rule": {
    "target_object": "AUM_005_007_008_009",
    "output_grain": ["cust_id", "yyyymmdd"],
    "measure_column": "存款AUM",
    "measure_aggregation": "sum",
    "aggregate_before_threshold": true,
    "threshold_stage": "after_customer_aggregation"
  },
  "active_stages": [],
  "expected_stage_count": 0,
  "source_tables": [],
  "source_usage_rules": [],
  "table_metadata": [],
  "missing_dependencies": []
}
```

子流程負責：

1. 根據 `metric_code`、`as_of_date` 與 operation 找到 execution rule。
2. 根據 valid date 與 mutually exclusive group 選出 active stages。
3. 只取得 active stages 實際需要的 source tables。
4. 只回傳這些 source tables 的 metadata。
5. 計算 expected stage count 與 missing dependencies。
6. 若來源或 dependency 不完整，回傳 `supported=false`，不要讓 Agent 猜測。

## 8. System Prompt 的長期原則

System Prompt 只保留不會因新增 Metric 而改變的規則：

- 必須先呼叫 SQL KB。
- SQL KB execution package 是唯一可信的業務邏輯與資料來源。
- 只能使用 `active_stages`、`source_tables` 與 `table_metadata`。
- 依 `execution_rule.output_grain` 與 aggregation rule 產生查詢。
- 門檻、排名、計數與比例必須在指定粒度彙總後套用。
- stage 數量、dependency 或 metadata 不完整就回傳安全錯誤 SQL。
- 不得猜測 table、column、JOIN key 或業務定義。
- 只能輸出單一唯讀 PostgreSQL `SELECT` 或 `WITH ... SELECT`。

System Prompt 不應再寫死：

```text
存款 AUM 的表名
存款專用彙總規則
目前五張底表名單
非存款就不支援
```

這些都由 KB execution package 動態提供。

另一個必修正點：

```text
depends_on_json → depends_on
```

## 9. 短期可驗證的正確 SQL 邏輯

在規則表尚未完成前，以三張已驗證歷史表測試存款 AUM：

```sql
WITH deposit_rows AS (
    SELECT cust_id, lst_mtn_dt, SUM(bal_amt) AS amt
    FROM dsdep.dep_nt_acct_hs
    WHERE lst_mtn_dt = '20260831'
    GROUP BY cust_id, lst_mtn_dt

    UNION ALL

    SELECT cust_id, lst_mtn_dt, SUM(avail_bal) AS amt
    FROM dsdep.dep_fn_acct_hs
    WHERE lst_mtn_dt = '20260831'
    GROUP BY cust_id, lst_mtn_dt

    UNION ALL

    SELECT cust_id, lst_mtn_dt, SUM(bal_amt) AS amt
    FROM dsdep.emp_dep_nt_acct_hs
    WHERE lst_mtn_dt = '20260831'
    GROUP BY cust_id, lst_mtn_dt
),
customer_deposit_aum AS (
    SELECT
        cust_id,
        lst_mtn_dt,
        SUM(amt) AS deposit_aum
    FROM deposit_rows
    GROUP BY cust_id, lst_mtn_dt
)
SELECT COUNT(*) AS 客戶數量
FROM customer_deposit_aum
WHERE deposit_aum > 10000000;
```

預期結果：`1`。

注意：這是目前假資料的短期驗證 SQL，不可當成所有 Metric 的長期寫死邏輯。
