## 1. 目前目標與簡化原則

正在製作私銀 AUM 智能查詢 prototype。現階段只完成必要的查詢鏈，不要提前加入治理或防呆層。

已確認的原則：

- 暫時不處理 Column Lineage KB。
- 暫時不加入 validation 節點。
- 暫時不加入額外 IF 節點。
- 不使用 Embedding 或 Vector DB 來查 Staging SQL／Metadata。
- 若 Metric Router 找到完全相符且可執行的 Metric，直接走既有 SQL。
- 若沒有可直接執行的 SQL，才進入 SQL Reasoning Agent。
- Staging SQL／Metadata 子流程最後只把必要 context 回傳給 Agent。

子流程最終資料只保留四類：

```json
{
  "metric_code": "aum_deposit_month_end",
  "staging_sql": [],
  "table": [],
  "metadata": []
}
```

實際欄位可保留 array 型態，但不要再附加 validation result、status、error flag、lineage 或其他暫時用不到的欄位。

## 3. Staging SQL＋Metadata 子流程的最終設計

建議保持最短流程：

```text
接收 metric_code
→ 查 aum_staging_sql_kb
→ 查 aum_metadata_kb（Get All）
→ Code：整理成四個必要欄位
→ 回傳主流程／SQL Reasoning Agent
```

不新增 validation 或 IF。

Code node 的責任只有：

1. 取得 Metric Router 選出的 `metric_code`。
2. 收集該 Metric 對應的 Staging SQL。
3. 從 Staging SQL 彙整實際來源 table。
4. 從 `aum_metadata_kb` 篩選這些 table 的 Metadata。
5. 回傳 `metric_code`、`staging_sql`、`table`、`metadata`。

建議輸出形狀：

```json
{
  "metric_code": "aum_deposit_month_end",
  "staging_sql": [
    {
      "staging_sql_id": "...",
      "stage_level": "source_transform",
      "output_object": "...",
      "depends_on": [],
      "sql": "..."
    }
  ],
  "table": [
    "DSDEP.DEP_NT_ACCT_HS",
    "DSDEP.FN_EXCH_RT"
  ],
  "metadata": [
    {
      "table_name": "DSDEP.DEP_NT_ACCT_HS",
      "table_description": "...",
      "columns": []
    }
  ]
}
```

`staging_sql`、`table`、`metadata` 是否使用單數欄位名，依使用者指定維持即可；重點是只回傳這四類資訊。

## 4. n8n 主流程的實際檢查結果

透過 Computer Use 唯讀查看過目前流程。

Switch 後有兩條路：

- `executable_match`：走既有可執行 SQL。
- `no_executable_match`：走 `SQL Reasoning Agent`。

目前發現：

1. `SQL Reasoning Agent` 的 prompt 仍帶有舊版 Context Planner 語意，應改成 SQL 生成任務。
2. Prompt 需要明確帶入真正的使用者問題，來源可用：

   ```javascript
   {{ $('Router Input').first().json.user_query }}
   ```

3. `Staging SQL/Meta Data KB` tool 的 `metric_code` 輸入當時是空的，可能是先前得到 `metric_code: null` 的原因。
4. 建議從 Metric Router 取值，例如：

   ```javascript
   {{ $('metric router').first().json.output.selected_metric_codes[0] }}
   ```

   實際節點名稱與 JSON 路徑必須以 n8n 當前 execution data 為準。

5. 現階段 SQL Reasoning Agent 不需要 Structured Output Parser。要求模型只輸出可執行 SQL 即可。
6. 下游 PostgreSQL 節點目前可使用：

   ```javascript
   {{ $json.output }}
   ```

   前提是 Agent prompt 嚴格要求不要輸出 Markdown code fence、說明文字或 JSON wrapper。

建議 SQL Reasoning Agent prompt 至少提供：

- 原始使用者問題。
- Router 選出的 `metric_code`。
- `staging_sql`。
- `table`。
- `metadata`。
- 明確要求只輸出 PostgreSQL SQL。

不要讓 Agent 自己猜不存在的 table 或 column；只能使用傳入 context 中的名稱。
