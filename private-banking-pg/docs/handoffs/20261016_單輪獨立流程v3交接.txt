1. Single Question
   輸入：使用者完整問題。
   輸出：n8n 訊息物件，含 sessionId、action、chatInput。

2. 整理使用者問題
   輸入：chatInput 原文。
   輸出：text 字串，內容應為 JSON：{needs:[...], ambiguities:[...]}。
   每筆 need 欄位：id、sourceText、targetText、requestedInformation、quantityText、requiresCalculationEvidence、includeAllComponents、scopeText、relationshipText。
   sourceText 須逐字存在於原問題中。這一層不選底表、不產生 SQL，也不回答業務問題。

3. Aura - Full Concept Graph
   輸入：固定的唯讀概念圖查詢。
   輸出：Neo4j Query API 的 data.fields／data.values，欄位為 conceptGraph、businessPaths。

   它載入完整候選範圍；載入過的路徑不等於本題實際採用的路徑。

4. Merge 問題與路徑
   Combine by Position，將兩路各一筆合成同一筆。
   輸出同時有上路的 text 與下路的 data；不是 Append 成兩筆各自往下跑。

5. 準備 Jev 選路資料
   輸入：合併資料，並取 Single Question 原文。
   處理：解析上路 JSON、檢查原文依據／型別／編號、驗證圖譜，再建立候選與決策問題。
   輸出重點：question、requirements、inputAudit、conceptGraph、conceptPathCandidates、questionMeta、aggregateRequirements、decisionRequest、preparationAudit。
   inputAudit 明確為 single_turn，history=[]、previousTopic={}、pendingClarification=null。
   第一輪每個計算 need 都問全部 39 條路徑；每個純概念 need 都問全部 41 個節點，尚未縮小候選或分批。

6. Jev 選路判斷

   輸出：answers[questionKey].choice，值為 included／uncertain／excluded，另有模型與用量資料。

7. 整理選路子圖

9. KB Result
   輸入：映射查詢結果與選路上下文。

12. Answer Model
    共用語言模型連接節點，設定 openai/gpt-5.6-luna。

13. Single Answer

五、「沒有映射資料」與 JSON 回覆的分析

沒有映射至少須區分三種情況。
第一種是問題只問分類或角色，本來就不需要計算映射，例如 Q2／Q3；不應附上像是故障的「未取得映射」段落。
第二種是計算需求根本沒選中概念路徑，映射沒有有效配對可查，例如 Q5／Q10／Q11；這是上游漏選，不能直接說 Aura 缺資料。
第三種才是選路正確，後續只有計算規則，或實際缺映射／原始 SQL。規則型映射有資料可說明，不能和完全沒資料混為一談。
因此目前不能概括判斷「路徑選擇與映射查詢都是正確的」，也沒有足夠依據把這批問題歸咎於 Aura Query 過舊。

使用者貼出的 Q11 有兩個獨立問題。
1. 外層 {sessionId, action, chatInput} 是 n8n 訊息／節點輸出包裝。Single Question 已設定 responseNodes，Single Answer.Message 也是字串，不應未經查證就改 responseMode 或說是模型生成了外層 JSON。
   已保存的 Q11 Editor 即時聊天畫面是正常段落，沒有外層物件；執行歷史／原始輸出曾看到整包物件。若要修顯示，應先辨識使用者所看的畫面與取值層。
2. chatInput 內的冗長證據／狀態報告，是 Answer Question 把內部資料寫成正文。此題沒有選中任何路徑，內部空證據觸發模型照述狀態，但不能因此推論圖內不存在銀行基金規則。

先修上游漏選，再收斂回答邊界與呈現。不能只把狀態欄位藏起來，就宣稱已修復資料取得。

六、去重子圖的調整方向，尚未實作

現況：conceptGraph 在選路後已合併節點與關係；但 Prepare Answer Evidence 仍把每條概念／映射路徑轉成文字附錄。完全相同的字串會去重，共用的半段路徑仍重複，所以回答很長。
SQL／規則資料雖有共享引用壓縮，仍不等於已完成使用者要的查詢子圖輸出。

下一版應從本題實際保留、支撐答案的概念與資料關係建立同一份子圖，讓模型與路徑呈現共用它，不把全部候選圖或全部路徑清單當作附錄。
節點以穩定身份去重；關係須保留來源、目標、關係類型，以及會改變意義的規則／版本／條件身份。不能只憑顯示名稱相同就合併。
共同中繼表、共同概念、共同關係顯示一次，以分支表達各產品來源；保留需要對照的產品／指標配對，避免去重後失去支持哪一項回答的關聯。
規則來源與原始 SQL 血緣要保留原有語意，不虛構跨圖的關係；不同版本、日期條件、重建／月更新仍須分開。
對外只呈現回答與精簡查詢子圖；內部 audit 可保留必要追蹤，不能直接展開成使用者段落。
純概念題只呈現概念子圖，不固定加「資料來源路徑未取得」的尾段。
具體採用圖形或精簡分支文字尚未定案；使用者已確認的是合併去重與縮小回覆，不能把某個呈現樣式寫成已上線功能。

七、各節點後續可調整的內容，仍屬分析

整理使用者問題：同一產品／指標的來源、公式、日期、去重是同一需求的不同面向，避免拆成多個重複 needs；保留不同產品／指標配對。比例題將分子／分母連回實際對象，保留尚不明確的地域定義，不能把外幣直接當海外。
Aura - Full Concept Graph：維持下路唯讀載入；這輪沒有證據顯示必須先修改圖資料或連線。
Merge 問題與路徑：保留 Combine by Position；目前分支設計已達成，不需加一個 LLM 來單純合併資料。
準備 Jev 選路資料：依圖中的名稱、別名、明確指標與階層關係縮小候選；仍要涵蓋整體指標必要組成，不能單靠字面不相同就刪掉。減少每項重複的長描述，並限制每批大小。
Jev 選路判斷：使用簡短但有業務語意的候選；分批後要保存所有判斷，不能截掉尾端候選。API 超限須作為執行錯誤處理，不能變成空資料的正常回答。
整理選路子圖：補回必要分類父節點及關係；保留配對與選取來源。明確名稱／別名與唯一圖譜配對可作一致性檢查，但自動補回仍須檢查限制與歧義，不能無條件覆蓋 Jev 結果。
Aura - Mapping Paths：先用選中配對核對映射結果，區分上游沒有配對、只有規則與真正缺映射；不要先把所有空結果當查詢壞掉。
KB Result：保留計算解釋需要的 SQL／規則／來源與關聯；不要把診斷資料設計成使用者必看的內容。
Prepare Answer Evidence：將內部稽核與回答素材分開，建立去重子圖，取代逐條路徑附錄。仍保留理解公式、日期、粒度、去重所需的完整依據。
Answer Question：保留通用回答方式；明確限制不輸出內部狀態、欄位、空 registry 清單；根據已取得內容直接回答。逐項核對底表與規則版本，不自行翻譯表名縮寫。
Single Answer：組成回答文字與去重子圖的呈現。外層訊息包裝的顯示問題須由畫面／取值層確認，不應只靠 prompt 修理。
Answer Model：目前沒有更換模型的決定。

來源核對要點：
sources/sql/8.INCOME_DETAIL.sql 為 CP950／Big5，請用正確編碼唯讀。
證券基金收入以 WKA28 作客戶、WKA31 作金額；WKA02 與 LAST2_WD 決定歸月，來源快照 YYYYMMDD 的 MAX 條件是另一個日期角色，不可互換。
部分來源依賴 PB_BONDTRADM_SEC 的最大快照日，這個條件存在於原 SQL；它本身不代表題目還需多選債券收入。
UNION 是對完整投影列去重，不等同保證每個客戶／月份唯一。
放款歷史及月更新有 LN_NT_ACCT_HS 與 LN_FN_ACCT_HS 兩個分支，分別見 SUM(GROSS_INCM) 與 SUM(INT_INCM-CB_INT_AMT)；不能把月更新第二分支也寫成 NT 表。
沒有來源支持將 NT／FN 翻譯成非金融帳／金融帳，應保留原表名。
sources/sql/2._AUM_SUMY.sql 可用來比對完整主彙總分支；圖內完整與原始 SQL 完整須分開驗證。
