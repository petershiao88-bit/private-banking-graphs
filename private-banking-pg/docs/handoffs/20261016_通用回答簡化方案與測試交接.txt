一、使用者最新意圖與工作邊界

使用者希望驗證：是否不必先把問題分成定義、比較、計算、追問等細類，而能讓回答模型直接讀完整對話與圖譜，用通用提示詞回答業務問題；需要時自然提出澄清。
使用者要求本輪先寫交接，將自行開新的 session 執行；不要代建新 chat，也不要在本輪繼續修改或跑模型測試。
下一個 session 的工作是按本計畫做最小對照與逐步調整，不再只補分類選項或疊加矛盾修補規則。
先逐組檢視實際輸入、輸出與來源，再決定調整；兩組目標能力通過後，才進入完整回歸。

沿用使用者約束：
- 18 節點，每輪單次 Jev，不發布。
- 不新增回答後驗證／修正節點，不增加前置 LLM 整理對話。
- 不修改 Aura 圖譜、原始 SQL、已發布共用 KB；不執行 Oracle 或真實金額查詢。
- 原 SQL 使用 CP950／Big5，不能順手改存 UTF-8。
- 每組獨立測試先清記憶，同組多輪之間保留記憶。跨話題干擾另設案例。
- 試驗期間可使用既有的回答模型；「不新增前置 LLM」不代表移除原本的 Answer Question／QA Chat Model。

五、建議的最小試驗方案（未實作）

目標：不再讓定義／比較／計算／追問等細分類決定是否准許回答。Jev 專注找可能相關證據，現有回答模型直接依原始對話與證據判斷怎麼回答、是否需要澄清。
同一輪維持一次 Jev 與一次既有主要回答模型；不增加 Resolve LLM、Agent 自動多次工具呼叫或回答後修復迴圈。

候選流程：
讀記憶＋完整概念圖 → 單次 Jev 找可相關的衡量路徑 → 有候選則查映射、無候選則仍保留概念圖 → 原始對話＋完整概念圖＋取得的映射交給同一回答模型 → 存原始問答。
有沒有查映射是資料檢索分支，不是把使用者問題先貼題型標籤。
先使用同一 QA Chat Model 與同一採樣設定，別在改架構時一起換模型，否則無法比較。

重要資料分工：
- 給回答模型的是完整概念圖；查映射的入口仍只能是檢索候選路徑組成的子圖。
- 現有 Aura - Mapping Paths 會依 conceptGraph 中的衡量邊找 binding。絕不可把完整概念圖直接塞進這個入口，否則可能查到所有產品的映射。
- 明確分開 fullConceptGraph 與 retrievalConceptGraph；若為相容舊 Aura 契約沿用 conceptGraph 作檢索入口，需另有 fullConceptGraph 傳給回答端。
- 檢索命中、候選與證據覆蓋都不等於使用者授權的回答／計算範圍。回答仍以原始問答為準，不因多撈到產品就一併回答或加總。
- 保留產品與指標的逐路徑配對，不用產品集合×指標集合產生笛卡兒積。

候選檢索政策（試驗前固定，不得看到答案後才調）：
第一版可將 included 與 uncertain 都當成「值得查證的資料候選」，excluded 不查；uncertain 不代表已選定業務範圍。
這項政策是試驗提案，不是已驗證解法；要記錄候選數、證據大小、耗時與來源混用情況。
若證據過大，記為本方案限制並回到檢索範圍設計；不得截斷 SQL、只取 top-1、默默捨棄必要來源或用摘要代替未讀原文。

Jev - Concept Path Decisions API：
沿用同一 API、模型與單次呼叫；它在本流程是 typed Decisions 選擇介面。通用自由文字回答由 QA Chat Model 產生，不是要求 Jev API 改成聊天回答。

Process Jev Decision：
只作回應格式驗證、候選路徑與檢索子圖組裝、保留 fullConceptGraph、原始對話與 audit。
移除 domain 改 channel、以 qa_context 分配題意、以答案分類覆蓋使用者範圍等語意修補。
不得將「無計算路徑」一概視為 unsupported／使用者不清楚；純概念題仍有完整概念圖。
不得把 uncertain 的候選直接變成一個要求使用者二選一的澄清模板。

Needs Mapping?：
改為只看有無檢索路徑／檢索子圖，不再檢查問題類型或 handling 是否為 calculation。
這是既有節點內的條件變更，保持同樣的兩條資料支線，不新增節點。

Aura - Mapping Paths：
優先保留固定唯讀 Cypher 與來源追溯規則，只調整必要的資料欄位引用。
保留多對多 mapping、完整 SQL、工作日／日期與來源依賴。不得改圖譜或 SQL 內容。

Prepare Calculation Evidence／Prepare Concept Response：
兩支最後都提供相同的回答輸入契約：question、history、fullConceptGraph、mappingEvidence（若有）、檢索狀態與來源限制。
mapping 的 bindings 表示檢索命中的證據適用範圍，不得預設每個 binding 都是使用者要求的回答項目。
無 mapping 時仍給完整概念圖，不清成空圖。實際檢索失敗要如實呈現，不包裝成使用者沒說清楚。

Answer Question：
改為通用業務回答指令：先讀整段原始對話，承接省略與比較；本輪明確變更取代相同條件；只依本輪提供的圖譜／來源說事實。
能回答就直接回答；只有缺少會改變答案的條件才問一個必要問題。歷史答案只能理解指代，不能作新的事實證據。
不要再先看 outputMode／handling／answerPurpose 決定是否准許回答，也不要強制照上游 clarification 原句念出。
保留目前的業務語言、來源忠實性、父子不重複加總、規則版本與日期血緣限制。
明確要求 SQL 時仍可按證據寫唯讀 SQL；是否有要求、查詢母體與深度從原始問題判斷，不必以 qa_sql_scope 類型標籤控制。不得執行 SQL。
原有 SQL 的日期、WHERE 血緣、CASE 順序、UNION 完整列去重、來源 staging 與下游私銀母體等語意要求不能隨簡化丟掉；但它們是來源規則，不是題型閘門。

Finalize QA／Write QA Memory：
保存本輪原始問題與最終回答；保留最近 12 輪、32KB 上限與原先單答案長度檢查。
不把選中的圖譜節點、映射或 AI 回答提到的 AUM／收入，存成已確認需求。
待澄清原題與 AI 的問句在原始 history 中保留，下一輪一起給模型理解；不需要先分類 clarification_reply 才能接回原題。
若調整 memory version，要同步 Prepare Dialogue 可讀版本並使用新 session 測試；不要讀取舊格式後又把舊 topic 當權威。
保留 metadata 相容欄位可以，但評分不能再依舊 qa_* enum 或 topic.domains 欄位存在與否判斷模型正確性。

其餘 Graph Chat、Aura - Full Concept Graph、Merge、Read／Write Memory、QA Text Memory、QA Chat Model、Response 優先不改功能，維持 18 節點與身份；必要欄位引用調整需完整列出。
