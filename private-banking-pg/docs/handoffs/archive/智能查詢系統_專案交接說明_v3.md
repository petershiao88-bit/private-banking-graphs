## 1. 目前階段與設計原則

目前只處理必要功能，不要再擴張成複雜 Planner、Vector DB、Embedding、Lineage 或治理框架。

Metric Router 目前只需要做兩件事：

1. 判斷候選 Metric Registry 中是否有完全相同、可以直接使用的 Metric。
2. 判斷使用者問題屬於哪一類 AUM。

目前已明確決定：

- 先拿掉 `missing_parameters` 路徑。
- 如果完全符合既有 Metric，Router 應同時回傳對應的可執行 SQL。
- 如果沒有完全符合，後續 Agent 才使用 Staging SQL KB 與 Metadata KB 作為 SQL reasoning context。
- 暫時不處理 column lineage。
- Staging SQL 與 Metadata 不使用 Embedding；以 n8n Data Table 與確定性查詢處理。

## 3. 重要更正：Metadata KB 的正確理解

`AUM_Metadata_KB_v0.2.csv` 已經把所有底表 Metadata 合併在同一份 CSV 中。

因此：

- 不需要為每張底表建立一張 Data Table。
- 不需要再把 Metadata CSV 拆成多份。
- n8n 中只建立一張 `aum_metadata_kb`。
- Runtime 時使用 Staging SQL 結果裡的 `source_tables`，從這張合併 Metadata Data Table 篩出相關列即可。

Metadata 不是 SQL 的執行結果，也不是資料處理上的下游表。它只是查詢 context：先由 Staging SQL 決定使用哪些底表，再從合併的 Metadata KB 取出那些底表的欄位定義。

先前對話中提出「一定要 Split Out 後逐表查 Metadata」講得太複雜。以目前只有 522 筆 Metadata 的規模，最簡單的方式是一次取得 `aum_metadata_kb` 的所有列，再用一個 Code node 依 `source_tables` 篩選。Split Out 只是一種可選作法，不是必要設計。

## 4. 兩張 Data Table 的關係

必須建立兩張獨立的 n8n Data Table：

| Data Table | 匯入 CSV | 角色 |
|---|---|---|
| `aum_staging_sql_kb` | `AUM_Staging_SQL_KB_v0.2.csv` | 說明 AUM 如何由各段 SQL 與來源表加工出來 |
| `aum_metadata_kb` | `AUM_Metadata_KB_v0.2.csv` | 集中保存所有底表及欄位定義 |

CSV 只用於初始化或更新 Data Table。Agent runtime 不應反覆讀取本機 CSV，而應查 n8n Data Table。

如果 n8n Data Table 先前已匯入亂碼內容，僅修改 CSV 不會自動修復；必須用新版 UTF-8 BOM CSV 重新執行 Upsert。

## 5. Staging SQL 子 workflow 現況

目前 Staging SQL 步驟完成後預計回傳一個 item：

```json
{
  "metric_code": "aum_deposit_month_end",
  "source_tables": [
    "DSDEP.DEP_NT_ACCT_HS",
    "DSDEP.FN_EXCH_RT"
  ],
  "staging_sqls": [
    {}
  ]
}
```

使用者最近貼出的實際測試結果是：

```json
{
  "metric_code": null,
  "source_tables": [],
  "staging_sqls": []
}
```

這表示目前測試執行沒有取得可用的 Metric／AUM 類型，或 Staging SQL 篩選沒有命中。Metadata 節點之前，應先確認上游實際傳入哪個欄位：`metric_code` 或 `aum_type`，並確認與 `metric_codes_json` 的值一致。

如果 `source_tables` 是空陣列，後續 Metadata 結果理應也是空陣列；不要在這種情況下讓 Agent自行猜測底表。

## 6. 下一個 session 應接續的 Metadata 節點設計

目前建議的最簡流程：

```text
Staging SQL Result
→ Data Table：Get all rows from aum_metadata_kb
→ Code：依 Staging SQL Result.source_tables 篩選並分組
→ 回傳 SQL Reasoning Agent
```

目前不需要 Split Out，也不需要一張表查一次。

### 6.1 Data Table 節點

- Resource：`Row`
- Operation：`Get`
- Data Table：`aum_metadata_kb`
- Return All：開啟

### 6.2 Code 節點的責任

1. 從前面的 Staging SQL Result 取得 `metric_code`、`source_tables`、`staging_sqls`。
2. 從 Data Table 輸入取得全部 Metadata rows。
3. 只保留 `source_tables.includes(row.table_name)` 的 rows。
4. 依 `table_name` 分組。
5. 回傳 SQL、底表與 Metadata 給 Agent。

參考邏輯（節點名稱需要依實際 n8n 畫面調整）：

```javascript
const staging = $('Staging SQL Result').first().json;
const wantedTables = new Set(staging.source_tables || []);

const metadataRows = $input.all()
  .map(item => item.json)
  .filter(row => wantedTables.has(row.table_name));

const grouped = {};

for (const row of metadataRows) {
  if (!grouped[row.table_name]) {
    grouped[row.table_name] = {
      table_name: row.table_name,
      table_description: row.table_description || '',
      columns: []
    };
  }

  grouped[row.table_name].columns.push({
    column_name: row.column_name,
    data_type: row.data_type || '',
    is_primary_key: row.is_primary_key || '',
    column_description: row.column_description || '',
    source_system: row.source_system || '',
    is_joint_credit_data: row.is_joint_credit_data || '',
    public_source_flag: row.public_source_flag || '',
    overseas_data_flag: row.overseas_data_flag || ''
  });
}

return [{
  json: {
    metric_code: staging.metric_code,
    source_tables: staging.source_tables || [],
    staging_sqls: staging.staging_sqls || [],
    table_metadata: Object.values(grouped)
  }
}];
```

預期輸出：

```json
{
  "metric_code": "aum_deposit_month_end",
  "source_tables": [
    "DSDEP.DEP_NT_ACCT_HS"
  ],
  "staging_sqls": [],
  "table_metadata": [
    {
      "table_name": "DSDEP.DEP_NT_ACCT_HS",
      "table_description": "台幣存款帳號歷史餘額",
      "columns": []
    }
  ]
}
```

## 7. 建議的新 session 起點

新 session 不要重新討論整體 Router 或重新設計 CSV。直接完成以下工作：

1. 讀取本交接檔。
2. 確認 Staging SQL 子 workflow 為什麼輸出 `metric_code: null`。
3. 讓一個實際 Metric 測試能輸出非空的 `source_tables` 與 `staging_sqls`。
4. 在後面接 `aum_metadata_kb` 的 Get All。
5. 使用一個 Code node 依 `source_tables` 篩選並按照 `table_name` 分組。
6. 將最後的 `staging_sqls` 與 `table_metadata` 一起交給 SQL Reasoning Agent。

目前不要：

- 再拆 Metadata CSV。
- 為每張底表建立獨立 Data Table。
- 加入 Embedding 或 Vector DB。
- 加入 column lineage。
- 擴張 Router 成多路複雜狀態。
