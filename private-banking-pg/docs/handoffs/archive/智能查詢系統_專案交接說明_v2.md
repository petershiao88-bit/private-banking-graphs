## 1. 目前目標

建立一套以 n8n 為流程骨架的 AUM 自然語言查詢原型。

目前採用 Metric First：

1. 既有 SQL Asset 能直接回答時，執行固定 PostgreSQL SQL。
2. 缺少必要使用者參數時，先補問。
3. 不能由單一 SQL Asset 直接回答時，進入 `no_executable_match`，交給 SQL Reasoning Agent 處理。

目前只是 prototype，使用者已明確要求不要先過度設計。SQL Reasoning 階段可以保留自由 Agent，不必先做完整 planner、SQL Validator、Safety Gate 或複雜的工具調度。

## 3. Metric Router 最新設計

Router 只負責選擇路徑，不回答問題、不產生 SQL、不修改 Metric。

### 3.1 三種頂層狀態

| `match_status` | 意義 |
|---|---|
| `missing_parameters` | 缺少日期、門檻、客戶範圍、比較期間等必要使用者參數，或語意有多種合理解讀 |
| `executable_match` | 一個既有 SQL Asset 能直接完整回答，不需要額外運算 |
| `no_executable_match` | 不能由單一 SQL Asset 直接回答；可能是既有 Metric 後處理，也可能是資料能力不足 |

原本的 `metric_reasoning_required` 與 `needs_ontology` 已合併為 `no_executable_match`，不得再輸出這兩個舊值。

### 3.2 Router 判斷優先順序

1. `missing_parameters`
2. `executable_match`
3. `no_executable_match`

### 3.3 Router Output 欄位

```json
{
  "match_status": "executable_match",
  "selected_metric_codes": [
    "aum_deposit_month_end"
  ],
  "requested_grain": "total_date",
  "resolved_parameters": [
    {
      "name": "as_of_date",
      "value": "2025-03-31",
      "source": "prompt_parser"
    }
  ],
  "missing_parameters": [],
  "reasoning_operations": [],
  "coverage_gaps": [],
  "reason": "指定月份的全行存款AUM可由單一資產直接回答。"
}
```

`requested_grain` 目前只允許：

`reasoning_operations` 允許：

`coverage_gaps.type` 允許：


- 不得輸出 Markdown code fence 或 JSON 外說明文字。

### 3.5 曾遇到的 Parser 錯誤

錯誤訊息：

```text
Model output doesn't fit required format
```

主要可能原因：

1. Parser 模式選成 `Generate from JSON Example`，卻貼入 JSON Schema。
2. Prompt 還要求 `metric_reasoning_required`／`needs_ontology`，但 Schema enum 只有三種狀態。
3. Schema 已要求 `requested_grain`，模型卻沒有輸出或輸出 `null`。
4. 模型省略空陣列、輸出額外欄位或使用錯誤 enum。

不要用 `On Error = Continue` 掩蓋 Router 格式錯誤。

## 4. Switch 最新設定

Switch 使用 `Rules` 模式，依 `match_status` 建立三條輸出。

如果 Router 結果包在 `output`：

```javascript
{{ $json.output.match_status }}
```

如果直接位於根層：

```javascript
{{ $json.match_status }}
```

三條 `is equal to` 右側使用 Fixed String，不加引號：

```text
missing_parameters
executable_match
no_executable_match
```

建議另設 fallback output：

```text
router_error
```

## 5. 門檻問題的重要判斷

測試問題：

> 2025 年 3 月底存款 AUM 超過 1,000 萬元的客戶有哪些？

目前正確結果是：

```text
match_status = no_executable_match
selected_metric_codes = [aum_deposit_month_end]
requested_grain = customer_date
reasoning_operations = [threshold_filter]
coverage_gaps = []
```

原因不是 Metric 不存在，而是目前 `aum_deposit_month_end / customer_date` SQL Asset：

- 只接受 `$1 = as_of_date`。
- 回傳各客戶 AUM。
- 沒有 `min_aum_amount` 參數。
- 沒有 `HAVING SUM(amt) > $2`。

所以門檻必須由 SQL Reasoning 額外產生。`no_executable_match` 在這裡代表「既有 Metric 可作為基礎，但需要衍生處理」，不是一定要走 Ontology。

如果未來希望此類問題走 `executable_match`，可擴充 customer SQL Asset，增加可選的 `min_aum_amount` 與 `HAVING`；目前尚未修改。

## 6. SQL Reasoning 現況與最新決策

### 6.1 目前 n8n 畫面

已看到的 SQL Reasoning 分支大致為：

```text
Switch
→ Build SQL Prompt
→ SQL Reasoning Agent
   ├─ OpenRouter Chat Model2
   ├─ Postgres Chat Memory
   └─ Code Tool
→ Code in Python
→ Execute SQL query
→ If
   ├─ true → Build Response Prompt → Basic LLM Chain → Respond to Webhook → Insert rows in a table
   └─ false → Build Repair Prompt → 回到 SQL Reasoning Agent
```

直接 Metric SQL 另有上方分支：

```text
Switch → Execute a SQL query1
```

第三個 Switch output 目前尚未清楚接完。

### 6.2 使用者最新決策

目前是 prototype，先不要把 SQL Reasoning 做得太複雜：

- 可以保留 SQL Reasoning Agent。
- 可以先讓 Agent 自由產生 PostgreSQL SQL。
- 暫時不必改成嚴格的 Basic LLM Chain planner。
- 暫時不做 SQL Validator、AST、安全閘門或複雜執行計畫。
- Agent 需要讀到相關 Staging SQL 與 Column Lineage。
- 最低限度仍建議使用只有 SELECT 權限的 PostgreSQL credential。

舊交接文件中「第一版不使用自由 Agent」已被本決策取代，至少 SQL Reasoning 分支現在允許 Agent。

## 7. Staging SQL Retrieval 最新方向

目前同意的簡化流程：

```text
Switch：no_executable_match
→ 取得相關 Staging SQL + Column Lineage
→ Build SQL Prompt
→ SQL Reasoning Agent
→ Code in Python
→ Execute SQL
```

現在 SQL 數量少，不需要 Vector DB 或 Embedding。可使用 n8n Data Table 或 PostgreSQL metadata table。

### 7.1 建議建立 `staging_sql_registry`

最小欄位：

| 欄位 | 用途 |
|---|---|
| `staging_sql_id` | SQL 唯一 ID |
| `staging_name` | 人類可讀名稱 |
| `metric_codes` | 支援的 Metric |
| `tags` | 輔助檢索標記 |
| `source_tables` | 來源表 |
| `output_table` | 產出表／View |
| `output_grain` | 輸出粒度 |
| `output_columns` | 可使用欄位 |
| `staging_sql` | 完整 SQL |
| `column_lineage` | 輸出欄位到來源欄位關係 |
| `status` | `draft`／`active`／`deprecated` |
| `version` | 版本 |

範例：

```json
{
  "staging_sql_id": "STG_AUM_CUSTOMER_DAILY_PG_V1",
  "staging_name": "客戶每日AUM彙整",
  "metric_codes": [
    "aum_deposit_month_end",
    "aum_total_month_end"
  ],
  "tags": [
    "aum",
    "customer",
    "daily_snapshot",
    "deposit",
    "month_end"
  ],
  "source_tables": [
    "cust_transaction_summary"
  ],
  "output_table": "stg_customer_aum_daily",
  "output_grain": "date_customer_product",
  "output_columns": [
    "yyyymmdd",
    "cust_id",
    "typ",
    "comp",
    "prod",
    "typ_sub_dtl",
    "amt"
  ],
  "staging_sql": "SELECT ...",
  "column_lineage": [
    {
      "output_column": "cust_id",
      "source_column": "cust_transaction_summary.cust_id",
      "transformation": "direct"
    },
    {
      "output_column": "amt",
      "source_column": "cust_transaction_summary.amt",
      "transformation": "direct"
    }
  ],
  "status": "active",
  "version": "1.0.0"
}
```

### 7.2 Reference 優先、Tags 輔助

建議在 Metric Registry 增加：

```text
staging_sql_refs
```

例如：

```json
["STG_AUM_CUSTOMER_DAILY_PG_V1"]
```

檢索流程：

```text
Router 選出 metric_code
→ Metric Registry 取得 staging_sql_refs
→ Staging SQL Registry 精準取得 SQL + lineage
→ 交給 SQL Reasoning Agent
```

`tags` 只作為沒有直接 reference 時的補充搜尋，不建議只靠模糊 tags。

### 7.3 Agent Context

Build SQL Prompt 前可整理成：

```json
{
  "user_query": "...",
  "router_result": {},
  "metric_context": [],
  "staging_context": []
}
```

Agent 規則先維持簡單：

- 使用 PostgreSQL 語法。
- 可以自由組合、包裝或改寫提供的 Staging SQL。
- 優先沿用 Staging SQL 的資料來源、過濾與計算邏輯。
- 只能使用 context／lineage 中存在的資料表與欄位。
- 不得自行發明資料表或欄位。
- 只產生 SELECT 或 `WITH ... SELECT`。
- 日期、金額與客戶 ID 使用參數。

目前建議由前置節點直接取得 context 並放入 Agent Prompt；等 SQL 資產變多後，再考慮做成 Agent Tool。

## 8. 子聊天室中的 PostgreSQL 假資料環境

### 8.1 已確認用途

目前 PostgreSQL v0.3 的 12 段 Metric SQL 全部以以下表作為 prototype／假資料來源：

```text
cust_transaction_summary
```

這張表是用來模擬已完成整併的 AUM staging，不代表正式資料倉儲的真實實體表，也不等於原始 Oracle SQL 的所有來源表。

### 8.2 已確認欄位

Metric SQL 實際使用欄位：

| 欄位 | 用途 |
|---|---|
| `yyyymmdd` | 資料日期；SQL 目前會轉成文字取 `YYYYMM`，並於各分類內取 `MAX(yyyymmdd)` |
| `cust_id` | 客戶識別碼 |
| `typ` | AUM 大類，例如 `存款`、`投資` |
| `comp` | 公司別，例如 `銀行`、`證券` |
| `prod` | 商品類別，例如 `保險` |
| `typ_sub_dtl` | 商品／資產細分類 |
| `amt` | AUM 金額；目前暫定 TWD |

目前 SQL 所依賴的分類組合：

| Metric | 固定條件 |
|---|---|
| 月底存款AUM | `typ='存款' AND comp='銀行'` |
| 月底投資AUM | `typ='投資'` |
| 月底銀行投資AUM | `typ='投資' AND comp='銀行'` |
| 月底證券AUM | `typ='投資' AND comp='證券'` |
| 月底保險AUM | `typ='投資' AND comp='銀行' AND prod='保險'` |
| 月底總AUM | 不限制上述分類 |

### 8.3 與現行 SQL 相容的最小 DDL（重建參考）

以下為依現有 SQL Asset 反推的相容結構，不應視為已核准正式 DDL：

```sql
CREATE TABLE cust_transaction_summary (
    yyyymmdd   INTEGER NOT NULL,
    cust_id    TEXT NOT NULL,
    typ        TEXT NOT NULL,
    comp       TEXT,
    prod       TEXT,
    typ_sub_dtl TEXT,
    amt        NUMERIC(20, 2) NOT NULL
);
```

如果子聊天室原本建立的 `yyyymmdd` 是 `DATE` 或 `TEXT`，正式接續時要以資料庫現況為準；目前 Registry SQL 使用 `yyyymmdd::text`，因此三者都可能執行，但 `MAX(yyyymmdd)` 的排序語意必須確認。

### 8.4 假資料應覆蓋的測試情境

假資料至少要有：

- 同一月份多個日期，才能驗證分類內 `MAX(yyyymmdd)`。
- 多個 `cust_id`，才能驗證 `customer_date`。
- 存款／銀行投資／證券投資／保險等分類。
- 同一客戶多筆商品，才能驗證 `SUM(amt)`。
- 至少一位存款 AUM 大於 1,000 萬、一位小於等於 1,000 萬，才能測試 `threshold_filter`。
- 至少兩個月份，才能測試 `comparison`／`trend`。

### 8.5 尚未從可存取內容找回的部分

目前專案檔案、可讀取的相關子聊天室及本聊天室紀錄中，沒有找到原始假資料的完整 `INSERT` 明細、筆數、客戶 ID 清單或總額對帳表。因此：

- 不得把本文件中的相容 DDL 說成子聊天室原始 DDL。
- 不得自行宣稱目前資料庫已有多少筆假資料。
- 接續工作若需要固定 expected result，應先從目前 PostgreSQL 執行：

```sql
SELECT COUNT(*) FROM cust_transaction_summary;
```

以及：

```sql
SELECT
    MIN(yyyymmdd) AS min_date,
    MAX(yyyymmdd) AS max_date,
    COUNT(DISTINCT cust_id) AS customer_count,
    SUM(amt) AS total_amount
FROM cust_transaction_summary;
```

再把實際結果補回本節。若原子聊天室仍可由使用者開啟，應請使用者貼出原始建表／INSERT 內容，以便完整保留。

## 10. 下一步建議

下一個聊天室不要重新討論整體架構，直接從以下工作開始：

1. 盤點準備提供給 Agent 的 Staging SQL。
2. 決定 `staging_sql_registry` 放在 n8n Data Table 或 PostgreSQL。
3. 為每段 Staging SQL 建立 `staging_sql_id`、`metric_codes`、`tags`、`output_columns` 與 `column_lineage`。
4. 在 Metric Registry 增加 `staging_sql_refs`。
5. 在 `Build SQL Prompt` 前加入取得 Staging SQL／lineage 的節點。
6. 用「2025 年 3 月底存款 AUM 超過 1,000 萬元的客戶」作為第一個 SQL Reasoning 端到端案例。
7. 若測試需要固定答案，先盤點 PostgreSQL 假資料的實際筆數與內容，不要憑空假設。

目前不要主動擴張為 Vector DB、Embedding、完整 SQL Planner 或複雜治理框架，除非使用者後續明確要求。
